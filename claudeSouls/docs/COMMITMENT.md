# 承諾:前後搖的統一與顯示

> **狀態:第一、二階段已完成。** 第三階段(CD 的去留、敵人收招變成真的軸)還沒動。
>
> 第一階段是資料,已驗證**逐位元沒有改變任何行為**——三個可玩英雄各跑 12 次機器人,
> 軌跡完全相同。第二階段是顯示,已上線。

## 這不是一套新系統,是把已經存在於一邊的規則補到另一邊

先看現況,因為數字本身就在講這件事:

| | |
| --- | --- |
| 玩家 36 個技能 | 前搖 3 個 · 收招 10 個 · CD 9 個 · **完全沒有承諾的 17 個** |
| 敵人 18 種攻擊 | 前搖 1:6 個、2:8 個、3:4 個 —— **每一擊都有** |
| 敵人的收招 | **18 個裡有 17 個是 2** |

兩個結論:

**一、敵人早就是這個模型了,玩家不是。** 這個遊戲的地基是「每一擊都會預告」,而它目前
**只對一個方向成立**。玩家有將近一半的技能完全沒有承諾——按下去,結束,沒有代價。

**二、敵人的收招是假資料。** 17/18 都是 2。那不是一條設計軸,是一個常數在冒充參數。
這次重構最有價值的產出可能就是**逼那 17 個數字各自說出理由**。

## 顯示的語彙已經存在,只是只畫在一邊

技能鈕上**現在就在畫這個**:

```js
// Hollow before the blow, solid after. Same budget, different gamble -
// and the hollow half is the one that can be taken away from you.
`${'○'.repeat(def.windup ?? 0)}${'●'.repeat(def.recovery ?? 0)}`
```

**空心 = 還沒發生(可以被拿走),實心 = 已經付掉。** 這條語意是對的,而且已經在玩家這邊
用了。敵人頭上畫的則是完全不同的東西:一個 `!`、幾條剩餘回合的刻度、`·` 和 `~`。

所以第二階段不是發明符號,是**把同一組符號搬到另一顆頭上**,並且把 `!` 和刻度拿掉。

### 顏色的意思

紅 = **前搖**(有東西要來),綠 = **收招**(有人動不了)。

**兩邊同一套,不分敵我。** 一個掛著綠點的敵人是你的機會;一個掛著綠點的你是它的機會。
同一個符號、同一個意思,誰戴都一樣——那正是「每一擊都會預告」這條契約要的形狀。

按顏色分敵我會比較直覺但比較沒用:玩家已經知道哪個是自己。

## 第一階段:資料

### 一、每個動作明碼標價

每一個技能和每一種敵人攻擊都要寫出 `windup` 和 `recovery`,包含 0。
「沒寫」和「寫 0」現在是同一件事,重構之後**「沒寫」是一個錯誤**——由 `validate` 擋。

理由和板塊那次一樣:**忘記填的東西不該悄悄變成最便宜的選項。**

### 二、定價公式已經寫好了,只是目前只用來驗收

`systest.mjs` 的「收招是規則定價的,不是手感」算的是:

```
v = (格數 - 1) × 1.0 + (射程 - 1) × 1.2 + 傷害 × 0.9
band = v >= 9.5 ? 2 : v >= 5.5 ? 1 : 0
```

這條規則存在的原因是 CD 當年是手填的,和招式大小的相關性只有 **r = 0.21**。
公式留在測試裡、數字留在資料裡——**兩邊分開才有驗收可言**,不能讓資料去 import 公式,
那會讓測試變成恆真。

### 三、CD 的處理:先不要刪

我原本想說 CD 可以整個消失,現在認為不行,而且理由具體:

- **CD 有 24 處程式引用**,而且 `reaping` 詞條(「每擊殺一個敵人,所有技能 CD −1」)
  整條建立在 CD 上——CD 消失它就沒東西可退。
- **CD 和收招不是同一種稅**:CD 只擋這一招,收招擋所有動作。把 CD 換成收招是變嚴,
  不是換句話說。

所以第一階段**不動 CD**,只做「前後搖補齊 + 敵人收招變成真的軸」。CD 的去留是第三階段的
題目,而且要先有量測。

### 四、敵人的收招要有理由

17 個 2 要各自變成一個講得出理由的數字。方向:

- **重、慢、大的東西**收招長——你付出的是被它抓到就死,換到的是它打完之後的一大段空檔
- **快、輕、成群的東西**收招短——狗打完馬上又能動,那才是波狀攻勢
- 收招長度應該和前搖長度**反相關**,否則就只是「強的更強」

這一條會直接改動戰鬥手感,所以要量:機器人的死亡數、每層死亡分布、以及木樁上的
「一次交換值多少回合」。

## 第二階段:顯示

- 敵人頭上畫 `○` × 前搖剩餘、`●` × 收招剩餘,紅綠如上。
- **拿掉** `!` 徽章和現有的刻度。這是取代,不是追加。
- 現在敵人頭上已經有:狀態徽章、菁英光暈、血條、**以及巡禮者的印記色點**。
  再疊一排會變成一團——所以印記的畫法要一起重排(她停用中,正好)。
- 地板紅格不動。**紅格是形狀,頭上的點是時鐘**,兩者不重疊。

### 為什麼不做殺戮尖塔式的意圖圖示

因為這個遊戲的意圖顯示**比 StS 好**:StS 給你一個圖示加一個數字,這裡直接把攻擊形狀
畫在地板上。再加一個圖示是把已經在畫的資訊再畫一次。

缺的從來不是「它要做什麼」,是「**還有幾回合**」。

## 做完之後

### 第一階段

- 36 個技能全部明寫 `windup` / `recovery`,**缺少是錯誤而不是 0**,由 `validateSkills` 擋。
- 18 種敵人攻擊(含 `next` 連段)同樣由 `validateAttacks` 擋。
- **`advancesTurn` 刪掉了。** 它在拍模型上線之後就沒有任何人讀,卻還掛在 36 個技能上
  裝作是規則——這是這個專案第三個同形狀的 bug(`aware` 兩個意思、`face` getter 被
  `face()` 方法蓋掉、然後是它)。驗證器會拒絕它回來,而測試釘的是**驗證器會拒絕**,
  不是 grep。
- 它的四個讀者改成問活的規則。最有意思的是瞄準提示:它從那個旗標讀出「free turn」,
  而真相是**翻滾對一拍英雄免回合、對巡禮者要一拍**——一個布林值永遠說不出這兩件事。

### 第二階段:它是一條時間軸,不是一個倒數

第一版畫的是**還剩幾回合**,那一排會隨著時間變短。它說不出玩家最需要的那件事——
**什麼時候**。畫「兩回合前搖」然後留給玩家自己推算「所以第三回合會打到我」,那是把
資訊藏在算術後面。

現在整排是固定長度,走過的**轉灰而不是消失**:

```
○ ○ ● ○        前搖兩回合、命中、後搖一回合
▪ ○ ● ○        過了一回合:第一顆變灰
▪ ▪ ● ○        它落下的那一回合
▪ ▪ ▪ ○        收招中
```

| | |
| --- | --- |
| 空心紅 | 什麼都還沒發生的一回合 |
| **實心紅** | **實際命中的那一拍** |
| 空心綠 | 它動不了的一回合 |
| 灰 | 已經過去 |

實心紅那一顆是第一版根本說不出來的東西。

**多顆實心紅 = 這次承諾欠你不只一擊。** 衝鋒仍然是一次宣告一段(見 `beginWindup` 的
註解,那是刻意的),這裡不洩漏下一段落在哪裡,只說還欠幾下——量到的實例是哨兵,
它的 `next` 連段讓那排真的長出兩顆實心紅。

`drawClock()` 一個函式畫敵我兩邊。敵人頭上的 `!` 和刻度**拿掉了**,不是並排。
進度是**推導出來的**(從 state 和 timer),不是另外數一個計數器——一個要跟著 timer
一起前進的第二個計數器,遲早會和它不同步,這個專案已經為那種東西付過一次錢。

驗證是直接讀畫出來的像素,不是看截圖猜:在一張真的 canvas 上畫「兩個前搖 + 一個收招」,
量三顆點的環和圓心——

| | 環 | 圓心 |
| --- | --- | --- |
| 第一顆(前搖) | `112,41,32` 紅 | `4,4,6` 暗 → **空心** |
| 第二顆(前搖) | `156,56,43` 紅 | `4,4,6` 暗 → **空心** |
| 第三顆(收招) | `68,165,79` 綠 | `86,211,100` 綠 → **實心** |

另外量到一件截圖看不出來的事:**六顆點在 35 像素的格子上會溢出到隔壁格。**
在一個講究「你站在哪一格」的遊戲裡,那等於把時鐘讀到別人身上。所以點會縮小去配合格寬,
不是讓那一排長出去。

巡禮者的印記色點同時從頭頂搬到腳邊(血條上方)——一顆頭上兩排彩色點是一團糊。

## 驗收:要釘的後果

| 要成立的事 | 怎麼量 |
| --- | --- |
| 每個技能和每種敵人攻擊都有明寫的前後搖 | 掃資料,缺的就是失敗 |
| 補齊本身沒有改變平衡 | 只補 0 的那一批,機器人軌跡逐位元相同 |
| 敵人收招不再是常數 | 分布的標準差 > 0,而且每個值都有註解說理由 |
| 定價公式仍然由測試持有,不由資料 import | 資料裡沒有 import 那條公式 |
| 顯示是取代不是追加 | 敵人頭上的元素總數不增加 |
| 玩家和敵人用同一組符號 | 同一個函式畫兩邊 |

每一條都要驗「把規則關掉會不會失敗」。

## 還沒決定的

- **CD 的去留**(第三階段)。`reaping` 要跟著重新設計。
- **玩家的前搖要不要也畫在頭上**,還是只留在按鈕上。畫兩次是噪音,只畫按鈕又不對稱。
- 前搖中被打中會被打斷——**這件事目前只有玩家這邊成立**(敵人要破失衡),
  而重構會讓這個不對稱變得很明顯。這可能是下一個要處理的東西,不在這份規格裡。
