# 命名:哪些是借來的,換成什麼

> **狀態:規格,尚未實作。**
>
> 一個原則,先寫在最前面:**要改就改完。** 只換兩個名字會得到一個明顯是魂系形狀的
> 遊戲配兩個怪名字,比不改更糟——它會看起來像在躲,而不是像在做自己的東西。

## 先量它有多大

| 詞 | 出現次數(js / css / tools / docs) |
| --- | --- |
| `bonfire` / `BONFIRE` | **130** |
| `篝火` | 65 |
| `souls` / `Souls` | **76** |
| `魂` | 58 |
| `firekeeper` | 8 |
| `火防女` | 12 |
| `First Flame` | 8 |
| `灰燼` | 9 |
| `claudeSouls` | 12 |

**超過三百處。** 大部分是機械性的取代,但其中有三類要小心:

- **`T.BONFIRE` 這種列舉常數**——改名要連存檔相容性一起想
- **`docs/` 裡的歷史紀錄**——那些是「當時我們怎麼想」的紀錄,改掉會讓過去的推理讀不通
- **`claudeSouls` 這個專案名**——它同時是目錄名、GitHub Pages 的路徑、存檔的 key

## 分成三層,只有第一層是非做不可

### 第一層:直接挪用的專有名詞

這三個是逐字借來的,而且是最容易被認出來的:

| 現在 | 為什麼要換 | 提案 |
| --- | --- | --- |
| **魂 / souls** | 就是那個字 | **燼 / embers** —— 火燒剩下的東西,和整個遊戲的火意象一致,而且「還有餘溫」正好是「還沒換成永久東西」的感覺 |
| **火防女 / firekeeper** | 逐字翻譯 | **守夜人 / the watch** —— 她的工作本來就是「火還亮著的時候待在這裡」 |
| **篝火 / bonfire** | 同上,而且是最頻繁的一個 | **爐 / hearth** —— 短、是名詞、而且「爐」在新架構下正好是兌換所和補給站,不是重生點 |

第三個特別重要:**篝火在這一版已經不是原本那個東西了**(不再是重生點,見
`docs/CURRENCY.md`),所以換名字不只是躲,是**它真的變成別的東西了**。

### 第二層:氣氛上像,但不是挪用

`第一火焰`、`灰燼之廳`、`巡禮者`、`老騎士`、`攝魂師`。

這些是同一個文類的詞彙,不是同一個作品的專有名詞。**我的建議是留著**,理由是:
它們已經和機制長在一起(第一火焰是王的名字也是通關條件;灰燼之廳是選角的房間),
而換掉會動到敘事,那是另一件事。

如果要動,`第一火焰` 是唯一值得考慮的——它是王,而下一階段會有更多王,
那時候它本來就要變成「其中一個」而不是「那一個」。

### 第三層:專案名 `claudeSouls`

**這個我不建議動,而且理由是實際的。** 它是:

- 目錄名(`/claudeSouls/`)
- GitHub Pages 的網址路徑(已經發布的連結)
- 存檔的 localStorage key(改了 = 所有人的存檔不見)

要換就得同時處理**存檔遷移**和**舊網址**,那是一個獨立的工程,不該和命名 pass 綁在一起。

如果最後還是要換,順序是:先做存檔的 key 遷移(讀舊寫新),跑一個版本確認沒事,
再改路徑。

## 怎麼做才不會做壞

**一、常數和顯示分開。**

`T.BONFIRE` 是資料層的識別碼,`'爐'` 是給人看的字。現在有些地方把兩者混在一起。
這次 pass 的**附帶價值**是把它們分開:改顯示名不該需要動列舉。

**二、存檔相容。查過了,兩個答案不一樣。**

- **地磚是安全的。** `T.BONFIRE` 是 `9`,一個數字,所以存檔裡存的是數字。
  改顯示名不會動到存檔。
- **專案名不安全。** 存檔的 key 是 `'claudesouls.save.v2'`——**專案名寫在裡面**。
  換掉 `claudeSouls` 等於把所有人的存檔弄丟。這證實了第三層的警告:
  要換就得先做讀舊寫新的遷移。

**三、`docs/` 用註記而不是取代。**

歷史紀錄改掉會讓推理讀不通:一段寫著「篝火頻率是症狀不是原因」的分析,把篝火換成爐
之後,讀的人會不知道那指的是同一個東西。**在文件開頭加一行對照表**,正文不動。

**四、一次一個詞,每次跑測試。**

三百多處的取代,分三次做(魂 → 火防女 → 篝火),每次跑完整測試。
一次全換出了錯會很難二分。

## 驗收

| 要成立的事 | 怎麼量 |
| --- | --- |
| 沒有殘留 | 掃 js/ 和 css/,第一層的三個詞是零 |
| 存檔還讀得到 | 用改名前的存檔開改名後的版本 |
| 顯示名和常數是分開的 | 改一個顯示字串不需要碰 `tiles.js` |
| 文件讀得通 | 每份 `docs/` 開頭有對照表 |
| 測試沒有靠名字過關 | 掃 `tools/`,測試不比對顯示字串 |

最後一條是這次最可能出的意外:**如果哪條測試是靠 `'bonfire'` 這個字串過的,
它會在改名之後安靜地不再測任何東西。** 那是這個專案已經犯過三次的錯
(`aware` 兩個意思、`face` 被蓋掉、`advancesTurn` 沒人讀),形狀完全一樣。

掃過了,現況比想像的好:測試裡出現的 `'firekeeper'` 是 **NPC 的識別碼**,不是顯示字串
(`npcs.push({ key: 'firekeeper' })`)。所以有一條界線可以直接畫下來:

> **識別碼不改,顯示名才改。** `key: 'firekeeper'`、`T.BONFIRE` 這些留著;
> 玩家看得到的字換掉。

這條界線讓這次 pass 從「三百多處」縮小到「顯示字串」,而且它本身就是那個「常數和顯示
分開」的原則,只是講成了一條可以照著做的規則。
