# 伏擊點:規格

> 這份文件是**寫給還沒實作的東西**的,和 `SITUATIONS.md` 一樣。
> 先寫下來是因為這個機制有幾個地方一不小心就會變成 bug 而不是機制。

## 它要解決什麼

上一輪把精力變稀缺之後,留下一個洞:**站著不動現在是最好的回復手段,而站著不動不痛。**
量出來老騎士有 77.7% 的戰鬥回合在等待。前期敵人打你要 6–8 下,退到走廊喘一口氣沒有代價。

伏擊點的工作是讓**退路有代價**。它不是為了增加傷害,是為了讓「往回走」和「停下來」不再免費。

## 它明確**不做**的事

這三條是設計決定,不是還沒做:

- **地圖上不標記。** 沒有柵欄、沒有洞、沒有記號。玩家看不出哪一格是伏擊點。
- **火防女不知道。** 她知道火告訴她的事,伏擊點不是火的事。
- **不透露哪些啟用了。** 玩家只能靠被跳過一次來學,而那是在種子之內學的。

## 核心:啟用與否是每個種子決定的

這條是整個機制的重點,而且它和種子契約**不衝突**——只要分清楚是哪一層的學習:

| | 保持 | 打掉 |
| --- | --- | --- |
| 同一個種子 | 啟用的還是那幾個。死了回來一樣,**學得到** | |
| 不同種子 | | 同一張板塊這次會跳人、下次不會。**學不到「走廊板塊 = 安全」** |

要打掉的是**板塊類型的學習**,不是樓層的學習。

### 沒啟用的時候,怪還是在

這條讓「沒啟用」不等於「什麼都沒發生」:

- **啟用**:那些格子在你走過時是空的,晚一點東西從那裡出來
- **沒啟用**:那些怪**一開始就站在那裡**,你正常打

**同一份預算、同一個數量,兩種完全不同的體驗。** 玩家事前分不出來:一條站著兩隻狗的走廊,
和一條空的、稍後會生出兩隻狗的走廊。這也是為什麼不需要另外給資訊——**未啟用的情況本身
就是有內容的**。

## 資料長相

延伸現有的 `enemies` 條目,不是新欄位家族:

```js
gully: { weight: 1,
  anchors: { a: 'nest' },
  enemies: {
    at: 'nest',              // 從哪幾格出來(現有欄位)
    role: 'charger',         // 什麼東西(現有欄位,伏擊點**必填**)
    n: [2, 3],               // 幾隻(現有欄位,省略 = 每格一隻)
    ambush: { oneIn: 2, after: [1, 3] },
  },
  art: [ ... ],
},
```

| 欄位 | 意思 |
| --- | --- |
| `ambush` 存在 | 這是伏擊點。不存在就是現在的行為(生成時直接放) |
| `ambush.oneIn` | 啟用機率的分母。`2` = 一半的種子會啟用 |
| `ambush.after` | 觸發到生成之間的回合數範圍 |

**`role` 對伏擊點是必填的。** 「照層數隨便抽」在走廊裡可能抽到 `blocker`,前後夾擊又沒有
側移空間,那是判死刑不是伏擊。作者必須明講。走廊建議用 `charger`(狗):快、脆、
目的是節奏不是傷害。

## 狀態機

```
        生成時擲骰
UNARMED ←──────→ ARMED
   │                │  玩家走進 R 格內
   │                ↓
   │              PRIMED
   │                │  那些格子離開玩家視野,且 after 回合已過
   │                ↓
   │               FIRE ──→ SPENT
   │                          │
   └──── 怪一開始就在那 ───────┘  休息後整層復活,回到 ARMED/UNARMED
```

- **R(觸發半徑)**:小,語感是「你走過去了」。建議 4–5 格。
- **PRIMED → FIRE 的兩個條件是 AND**,不是 OR。

## 讓「不可視」依然公平的三條規則

不可視的代價是:東西出現了而玩家看不出原因。最低限度要有這三條,否則它讀起來是 bug。

**一、只在那些格子**全部離開玩家視野**時才生成。** 看得到就先憋著。
伏擊本來就不該在你眼前現身——所以這條規則和它的意義是同一件事,不是補丁。

**二、一句訊息。** 不透露方向也不透露距離,只說發生了:

> 「石縫裡有東西鑽出來。」

那是這個機制唯一的聲音(這個遊戲沒有聲音系統,`noise` 陣列只被 renderer 拿去畫地板紋理)。

**三、生出來的東西是醒著的。** 它們是來找你的。睡著的伏擊等於沒有伏擊。

## 一次,直到休息

`SPENT` 之後不再觸發,直到整層復活。這剛好接上既有的篝火契約(休息 = 整層敵人復活),
**不用新概念**。

它同時解掉兩個問題:

- 走廊不會變成無限跑步機
- 死掉之後走回篝火那段路不會變成刑場

## 兩個實作上的陷阱

**一、啟用的骰子不能從樓層的生成流裡抽。**
`placeKeeper` 犯過這個錯:在生成流程中間抽一個亂數,會把它之後的**每一個決定都往後推**,
整座地城變成另一座。當時三次 A/B 比較其實在比兩座不同的地城。

伏擊點的啟用要用**衍生的流**:`new RNG(`${seed}#${depth}#ambush`)`。這樣加不加這個功能,
地圖都是同一張,而且它自己仍然是種子的函數。

**二、被拒絕但不推進回合的動作是無限迴圈。**
這個專案犯過五次(篝火、收招、走進 NPC、機器人撞牛頭人、翻滾)。伏擊點本身不接受輸入,
所以不直接踩到,但**機器人**要能處理「本來空的地方突然有敵人」——它每回合重讀狀態,
應該沒事,但這是要測的東西,不是要假設的東西。

## 這會推翻一條寫下來的平衡

`populate.js` 的第二條規則:

> **每層都要有你跑得掉的和跑不掉的。** 否則「跑過去」不是永遠對,就是永遠不可能。

**伏擊點專門懲罰「跑過去」。** 這是刻意把天平推向「清乾淨」,不是副作用。
方向是對的(它讓狗有存在的理由),但這條規則的註解要跟著改,不能讓它悄悄地變成假的。

## 驗收:要釘的後果

照這個專案的紀律——**釘後果,不釘機制**:

| 要成立的事 | 怎麼量 |
| --- | --- |
| 同一個種子,啟用的點一樣 | 同 seed 生成兩次,比對啟用集合 |
| 不同種子,啟用的集合會變 | N 個種子,啟用率落在 `1/oneIn` 附近,而且不是全 0 或全 1 |
| 加了這個功能,地圖沒變 | 開關功能,比對 `lvl.tiles` 逐格相同 |
| **永遠不在玩家眼前生成** | 每次 FIRE 時斷言那些格子 `!isVisible` |
| 一層樓最多觸發一次(到休息為止) | 跑完一層,計數 |
| 未啟用的點,怪一開始就在 | 未啟用 ⇒ 那些格子在生成後就有敵人 |
| 生出來的是醒著的、是指定的角色 | 直接讀 |
| 機器人不會卡住 | `failures: 0`,而且 WHYSTALL 沒有新的重複動作 |

每一條都要驗「把規則關掉會不會失敗」。這個專案有三次測試是**因為錯的理由通過**的
(牆擋住、價格擋住、對稱藝術),所以負向驗證不是可選的。

## 還沒決定的

- **R 到底幾格。** 4 和 5 的差別要量,不要猜。
- **`after` 的範圍。** 太短像瞬移,太長像沒發生。
- **第一層要不要有。** 第一層是教學,被看不見的東西跳可能不是好的第一印象。
- **要不要限制每層的伏擊點總數。** 一層三個和一層八個是兩種遊戲。
